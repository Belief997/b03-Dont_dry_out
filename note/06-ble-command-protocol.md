# 06 · BLE 连接态命令协议 (cmd proto v1)

设备**被连接之后**，经 NUS 透传通道收发的请求/响应协议。供上位机（`dev/desktop/index.html`）、
手机 App 与固件三方对照实现。

> **本文地位与其他 note 相反 —— 这是领先于代码的实现规范，不是现状描述。**
> 截至撰写时固件侧【尚未实现任何一条命令】：`ble_link.c` 的 `nus_data_handler` 只做
> hexdump + 原样回显（见 `main.c` 的 `ble_link_rx_handler`）。本文是"要照着做成什么样"，
> 实现完成后请把 §12 的清单逐项勾掉，并把与代码不符之处**改本文**而不是改代码注释。
>
> ⚠ 对照 `05-broadcast-payload-protocol.md` 的教训：那份文档写的是广播协议 v0x01，
> 而 `main.c` 早已是 v0x02、`app_proto.h` 已定义 v0x03 —— 文档没跟上代码。
> 本文的常量最终应收敛到一个 `services/cmd_proto.h` 里由固件与本文共用，
> 避免同样的漂移。

## 0. 与广播协议的边界（先划清，免得混淆）

设备上有**两套完全独立的协议**，各有各的版本号，互不影响：

| | 广播协议 | 命令协议（本文） |
|---|---|---|
| 载体 | 不可连接广播的厂商自定义段 | 连接后的 NUS 特性（Write / Notify） |
| 方向 | 单向，设备 → 空气 | 双向，请求 / 响应 |
| 触发 | 单击按键 → 播 `BLE_BEACON_ADV_EVENTS` 次 | 长按开 30s 窗口 → 连上 → 随时发命令 |
| 字节预算 | **31 字节硬上限**（BLE 4.x 传统广播） | 每帧 20 字节，可多帧续传，无总量上限 |
| 定义位置 | `services/app_proto.h`、note 05 | `services/cmd_proto.h`（待建）、本文 |
| 版本号 | `APP_PROTO_VERSION`（现 0x02，v3 已设计未接线） | `CMD_PROTO_VERSION` = 1 |

**本协议不改动广播包的任何一个字节。** 两者唯一的交集是：

1. **标定模式会抑制数据广播的"触发"**（§6）—— 抑制的是"什么时候播"，
   播出去的包格式仍然完全由广播协议决定。
2. `CMD_INFO` 会**同时报告两个版本号**，让上位机一次拿到"该按哪套规则解广播包、
   该按哪套规则发命令"。

⚠ 另一处容易混淆的地方：广播协议 v3 里也有"记录"概念（8 条 × 2 字节 = 类型 + 克数），
那是**为了塞进 31 字节而极度压缩的摘要**；本协议 `CMD_REC_READ` 下载的是
**完整原始记录**（20 字节 / 条，含三通道原始计数）。同名不同物，不要互相套用。

## 1. 传输层与硬约束

### 1.1 通道

Nordic UART Service，128bit 厂商 UUID（`ble_link.c` 已实现）：

| 特性 | UUID | 方向 | 用途 |
|---|---|---|---|
| Service | `6e400001-b5a3-f393-e0a9-e50e24dcca9e` | — | — |
| RX | `6e400002-…` | 上位机 → 设备 | **请求帧**，Write / Write Without Response |
| TX | `6e400003-…` | 设备 → 上位机 | **响应帧**，Notify（须先 `startNotifications`） |

前置条件：长按按键打开 30s 可连接窗口（`BLE_LINK_ADV_DURATION_MS`）→ 连接 →
使能 TX 通知。未使能通知时固件 `ble_link_send()` 返回 `NRF_ERROR_INVALID_STATE`。

### 1.2 帧长上限 = 20 字节（v1 固定值，不协商）

- 固件支持 MTU 最大 247（`NRF_SDH_BLE_GATT_MAX_MTU_SIZE`）→ 单帧最多 244 字节；
- **但 Web Bluetooth 不暴露协商后的 MTU**，上位机只能按最保守的 ATT MTU 23 算，
  即 20 字节（`index.html` 里 `state.ble.mtu = 20` 就是这个原因）；
- 因此 **v1 把帧长上限钉死在 20 字节**，不做协商。收益是任何客户端、任何 MTU
  下行为完全一致；代价是长数据要多帧（§2.3）。
- `CMD_INFO` 仍会报告设备侧的实际有效 MTU，**仅供诊断与未来 v2 扩展**，
  v1 客户端必须忽略它并坚持 20 字节。

### 1.3 帧边界由 GATT 保证，故协议内不加 magic / 长度 / CRC

- 一次 `writeValue()` 到达固件就是一个 `BLE_NUS_EVT_RX_DATA`，长度精确；
  超 MTU 的长写由 `nrf_ble_qwr` 重组后仍作为一个事件投递。**边界不会粘连或撕裂。**
- 链路层已有 CRC24 + 重传，应用层再算 CRC 是纯冗余。
- 长度字段同理可省：每条命令的参数长度是固定或可从命令码推出的，
  固件**必须校验实到长度**，不符回 `ERR_BAD_LENGTH`（§4）。
- ⚠ 由此得出一条对客户端的硬约束：**一条命令必须在一次 write 里整帧发出，
  不得自行分片**。所有请求帧 ≤ 20 字节，这一点天然成立。

### 1.4 上下文与流控（固件侧的两个坑）

1. **`nus_data_handler` 跑在 SoftDevice 事件中断上下文**（`ble_link.h` 已注明）。
   而 `app_storage` 的读写内部忙等 `sd_app_evt_wait()`，**中断里调用会死锁**。
   → 收到请求只能**入队**，由主循环执行。参照 `main.c` 现成的
   `m_store_snap` / `m_store_pending` 中转模式。
2. **发送必须做流控。** `ble_nus_data_send()` 在 SoftDevice 发送缓冲满时返回
   `NRF_ERROR_RESOURCES`，现在 `ble_link_send()` 只打一条警告就把数据**丢了**。
   短响应偶尔丢还能靠客户端超时重试，但 `CMD_REC_READ` 一次要连发几十帧，
   丢帧是必然的。
   → **必须新增一个发送队列，由 `BLE_NUS_EVT_TX_RDY` 驱动续发**（该事件
   `ble_link.c` 里已经有分支，目前是空的）。这是本协议对固件最大的一处新增。

吞吐参考：612 条记录 × 20 字节 = 12,240 字节，按 16 字节/帧 → 765 帧。
连接间隔 20ms、`NRF_SDH_BLE_GAP_EVENT_LENGTH = 6`（7.5ms）下约 4~6 帧/间隔，
估算 **3~5 秒**跑完全量下载。可接受，无需提高 MTU。

## 2. 帧格式

全协议**小端**，与固件结构体的内存布局一致，两侧都不需要字节序转换。

### 2.1 请求帧（上位机 → 设备，2 ~ 20 字节）

```
 偏移  长度  字段
 ----  ----  ------------------------------------------------
   0     1   CMD     命令码，0x01..0x7F（0x00 与 0x80+ 非法）
   1     1   TAG     客户端自选的请求标签，设备原样回填
   2     N   ARGS    命令参数，N = 0..18
```

**TAG 的作用**：NUS 是异步通道，设备的主动上报（§2.4）与响应会混在同一条
Notify 流里。TAG 让客户端把响应与自己发出的那条请求对上。建议客户端用
0x00..0xFE 循环递增。**0xFF 保留给设备主动上报，客户端不得使用。**

### 2.2 响应帧（设备 → 上位机，4 ~ 20 字节）

```
 偏移  长度  字段
 ----  ----  ------------------------------------------------
   0     1   CMD|0x80  对应请求的命令码，最高位置 1
   1     1   TAG       回填请求的 TAG（主动上报为 0xFF）
   2     1   STATUS    0x00 = 成功，非 0 见 §3
   3     1   FRAG      bit7 = MORE（还有后续帧）
                       bit6..0 = 帧序号 0..127
   4     M   DATA      数据，M = 0..16
```

**失败时 `STATUS != 0`，`FRAG = 0x00`，`DATA` 为空**（长度 4 字节）。
即"每条命令都有执行结果返回"（需求 6）的统一落地方式：客户端只要看 `STATUS`。

### 2.3 多帧响应 = 一段连续字节流

超过 16 字节的响应拆成多帧：

- 帧序号从 0 递增；除最后一帧外 `MORE = 1`；
- 除最后一帧外 `DATA` **必须满 16 字节**（客户端据此校验没丢帧）；
- 客户端把各帧 `DATA` 按序号拼接成一段字节流，**再按该命令的结构解析**；
- 单个响应上限 128 帧 × 16 = **2048 字节**。超过则命令必须分页
  （`CMD_REC_READ` 的 `count` 因此限制在 ≤ 64 条）。

> ⚠ 为什么让帧只当"搬运工"、不让一帧装一条记录：记录是 20 字节，而帧内
> 只有 16 字节可用，硬要对齐就得把记录压成 16 字节（丢字段）或把帧头砍到 2 字节
> （丢 STATUS）。让帧与被搬运的结构解耦，任何结构都能过，未来加字段不动帧格式。

### 2.4 设备主动上报

`TAG = 0xFF` 的响应帧表示**不是任何请求的应答**。v1 用到两处：

| 场景 | 帧 | 说明 |
|---|---|---|
| 传感器推流 | `0x02\|0x80, TAG=0xFF` | 由 `CMD_SENSOR_STREAM` 开启，内容与 `CMD_SENSOR` 响应完全相同 |
| 标定模式超时退出 | `0x12\|0x80, TAG=0xFF, STATUS=0` | 设备自行退出标定模式，告知客户端（§6） |

客户端必须能容忍在任意时刻收到 `TAG=0xFF` 帧，不得把它当成上一条请求的响应。

## 3. 状态码 (STATUS)

| 值 | 名称 | 含义 | 客户端应对 |
|---|---|---|---|
| 0x00 | `OK` | 成功 | — |
| 0x01 | `ERR_UNKNOWN_CMD` | 命令码未定义 | 检查版本号，可能是新客户端对老固件 |
| 0x02 | `ERR_BAD_LENGTH` | 请求帧长度与命令不符 | 客户端 bug |
| 0x03 | `ERR_BAD_PARAM` | 参数取值越界 | 检查参数范围 |
| 0x04 | `ERR_WRONG_MODE` | 该命令要求（或禁止）标定模式 | 先 `CAL_ENTER` / `CAL_EXIT` |
| 0x05 | `ERR_BUSY` | 上一条命令的多帧响应未发完，或 flash 操作进行中 | 等上一条完成后重试 |
| 0x06 | `ERR_STORAGE` | fstorage 读写失败 | 记日志，重试一次；持续失败视为硬件故障 |
| 0x07 | `ERR_NOT_FOUND` | 记录索引超出已写入条数 | 重新读 `CMD_INFO` 拿 `rec_count` |
| 0x08 | `ERR_NOT_CALIBRATED` | 需要标定参数但设备未标定 | 先完成标定 |
| 0x09 | `ERR_CONFIRM` | 破坏性操作的确认码不对 | 客户端 bug，或防误触生效 |
| 0xFF | `ERR_INTERNAL` | 不该发生的内部错误 | 上报日志 |

## 4. 会话规则

1. **单请求模型。** 设备同时只处理一条命令。上一条的多帧响应还没发完就收到新请求
   → 回 `ERR_BUSY`（4 字节帧，TAG 为新请求的 TAG）。
   *理由：省掉多路复用的状态机与缓冲；客户端本来也是一问一答。*
2. **长度校验先行。** 收到帧先查 `CMD` 是否已定义、再查长度是否匹配，
   任一不符立即回错，**不执行任何副作用**。
3. **断连即复位会话。** 连接断开时：清空发送队列、丢弃未完成的多帧响应、
   关闭传感器推流、**退出标定模式并丢弃未提交的改动**（§6）。
4. **超时由客户端负责。** 设备不为请求设超时。客户端建议：普通命令 1s，
   涉及 flash 写/擦的命令（`CFG_SAVE`、`REC_ERASE`）**3s**
   （擦一页约 87ms，`REC_ERASE` 要擦 3 页）。
5. **无鉴权**（见 §11 建议 B）。任何连上的对端都能发任何命令，
   破坏性操作靠确认码防误触，靠"必须物理长按才能连"防外人。

## 5. 命令详表

命令码分组：`0x0x` 只读信息 · `0x1x` 标定 · `0x2x` 配置 · `0x3x` 存储

| 码 | 名称 | 标定模式要求 | 一句话 |
|---|---|---|---|
| 0x01 | `INFO` | 任意 | 设备全部静态/摘要信息 |
| 0x02 | `SENSOR` | 任意 | 当前传感器快照 |
| 0x03 | `SENSOR_STREAM` | 任意 | 开/关传感器周期推流 |
| 0x10 | `CAL_GET` | 任意 | 读标定参数 |
| 0x11 | `CAL_ENTER` | 须**不在** | 进标定模式 |
| 0x12 | `CAL_EXIT` | 须**在** | 出标定模式 |
| 0x13 | `CAL_ZERO_SET` | 须**在** | 写零点（当前值或指定值） |
| 0x14 | `CAL_K_SET` | 须**在** | 写最小二乘系数 |
| 0x20 | `CFG_SET` | 任意 | 改饮料类型 / 广播参数 / 放置阈值 |
| 0x2F | `CFG_SAVE` | 任意 | 把 RAM 工作副本提交到 flash |
| 0x30 | `REC_READ` | 任意 | 分页下载记录 |
| 0x31 | `REC_ERASE` | 任意 | 清空全部记录（需确认码） |

### 0x01 `CMD_INFO` — 设备信息

**需求 1 的主要落地。** 参数：无（帧长 2）。

响应 DATA，共 **40 字节**（3 帧）：

| 偏移 | 长 | 字段 | 来源 / 说明 |
|---|---|---|---|
| 0 | 1 | `cmd_proto_ver` | 本协议版本 = **1** |
| 1 | 1 | `fw_ver` | 固件版本，建议 `主<<4 \| 次` |
| 2 | 1 | `adv_proto_ver` | 广播包版本，即 `APP_PROTO_VERSION`（现 0x02） |
| 3 | 1 | `cfg_ver` | 配置结构版本，`APP_STORAGE_CFG_VERSION` |
| 4 | 6 | `mac[6]` | `sd_ble_gap_addr_get()` 的 `addr[]`，**小端原样** |
| 10 | 1 | `addr_type` | 1 = random static（默认，见 `ble_link.h`） |
| 11 | 4 | `device_id` | `FICR->DEVICEID[0]`，广播包里的 2 字节 ID 取其低 16 位 |
| 15 | 2 | `flags` | 见下表 |
| 17 | 1 | `drink_count` | 已启用饮料类型数，1..16 |
| 18 | 1 | `drink_idx` | 当前选中类型，`< drink_count` |
| 19 | 1 | `cal_epoch` | 标定世代号，每次 `CFG_SAVE` 改了标定就 +1（§7.3） |
| 20 | 2 | `rec_count` | 已写入记录条数 |
| 22 | 2 | `rec_capacity` | 容量，当前 **612** |
| 24 | 4 | `rec_seq_newest` | 最新记录的 `seq`；`rec_count==0` 时为 0xFFFFFFFF |
| 28 | 4 | `rec_seq_oldest` | 最旧记录的 `seq`；同上 |
| 32 | 2 | `batt_mv` | 当前电池电压 mV（现采一次 SAADC） |
| 34 | 2 | `adv_events` | 一轮广播事件数 |
| 36 | 2 | `adv_interval_ms` | 广播间隔 |
| 38 | 2 | `eff_mtu` | 设备侧有效 ATT MTU，**仅诊断，v1 客户端须忽略**（§1.2） |

`flags` 位定义：

| 位 | 名称 | 含义 |
|---|---|---|
| 0 | `CALIBRATED` | 已标定（`cal_k` 不全为 0） |
| 1 | `CAL_MODE` | 当前处于标定模式 |
| 2 | `STORAGE_READY` | `app_storage_init()` 成功（失败时记录功能不可用） |
| 3 | `CFG_DIRTY` | RAM 工作副本有未提交到 flash 的改动 |
| 4 | `STREAMING` | 传感器推流开着 |
| 5..15 | — | 保留，必须为 0 |

> **为什么标定系数不放在 INFO 里**：`cal_zero[3]` + `cal_k[3]` = 24 字节，
> 放进来 INFO 就变 64 字节 / 4 帧。而 INFO 是客户端会反复拉的（刷新状态），
> 标定系数却是低频只读的。拆成 `CAL_GET` 后 INFO 少传 24 字节，
> `flags.CALIBRATED` + `cal_epoch` 已足够让客户端判断"要不要重新拉一次系数"。
>
> **`rec_seq_*` 是为增量下载准备的**：客户端记下上次拉到的 `seq`，
> 下次只拉更新的部分，不必每次全量 12KB。

### 0x02 `CMD_SENSOR` — 当前传感器快照

**需求 2 的落地。** 参数：无（帧长 2）。

响应 DATA，共 **26 字节**（2 帧）：

| 偏移 | 长 | 字段 | 说明 |
|---|---|---|---|
| 0 | 4 | `ch0` | int32，HX711 #1 chA，增益 128，**滑动平均后**的值 |
| 4 | 4 | `ch1` | int32，HX711 #1 chB，增益 32 |
| 8 | 4 | `ch2` | int32，HX711 #2 chA，增益 128 |
| 12 | 4 | `weight_g` | **float32 IEEE754**，`app_storage_weight_calc()` 的结果，单位克 |
| 16 | 2 | `batt_mv` | 电池电压 mV |
| 18 | 2 | `flags` | 数据状态，见下 |
| 20 | 4 | `sample_tick` | `m_sample_tick`，采样节拍序号 |
| 24 | 2 | `p2p_max` | 三通道峰峰值里的最大者（counts），用于观察震荡幅度 |

`flags` 位定义（低 8 位与 `app_proto.h` 的 `APP_PROTO_FLAG_*` **保持一致**，
高 8 位见 §7.3）：

| 位 | 名称 | 含义 |
|---|---|---|
| 0 | `STABLE` | 数据已稳定，可信 |
| 1 | `SETTLING` | 正在震荡 |
| 2 | `STALE` | 窗口过期，不可判定 |
| 3 | `UNCAL` | 未标定 → `weight_g` 恒为 0，不代表"真的 0 克" |
| 4 | `PRESENT` | **有物体放置**（新增，见下） |

> **`STABLE/SETTLING/STALE` 必须返回，虽然需求 2 没提。**
> 标定作业（§8）的每一步都是"放砝码 → 等稳 → 读数"，客户端没有稳定标志
> 就只能靠盲等，采到震荡期的读数会让最小二乘解出偏差几十克的系数。
>
> **`sample_tick` 也必须返回**：客户端轮询频率可能高于传感器的 10Hz，
> 没有它无法区分"两次读到同一帧"与"传感器真的没变"。
>
> **`PRESENT` 是当前固件没有的新功能**（见 §11 疏漏 1）。
> 判据建议：`|weight_g| >= cfg.present_thr_g`，**不要求 STABLE**
> （刚放上就该报"有物体"，等稳要 2~3 秒）。未标定时该位无意义，
> 此时固件应同时置 `UNCAL` 并把 `PRESENT` 置 0。

### 0x03 `CMD_SENSOR_STREAM` — 传感器推流开关

参数（帧长 4）：

| 偏移 | 长 | 字段 | 说明 |
|---|---|---|---|
| 0 | 2 | `period_ms` | 推送周期，**0 = 关闭**；有效范围 100..10000 |

响应 DATA：2 字节 = 生效的 `period_ms`（设备可能上调到最小值 100）。

之后设备每 `period_ms` 主动推一帧 `CMD_SENSOR` 格式的响应（`TAG=0xFF`），
直到关闭、断连、或收到新的 `SENSOR_STREAM`。

> **为什么需要推流而不只靠轮询**：标定时上位机要盯着实时重量看砝码放稳没有。
> 轮询一次是"写请求 + 2 帧通知"三个往返方向；推流只有 2 帧，且节奏由设备把住，
> 不受客户端调度抖动影响。周期建议 200ms（传感器本身只有 7~10Hz，更快无信息量）。
>
> ⚠ 推流会与多帧响应竞争发送队列。固件实现时：**推流帧优先级最低**，
> 队列里有请求响应待发时跳过本次推送（丢一帧无所谓，下一周期就补上），
> 绝不能让推流把 `REC_READ` 的帧挤掉。

---

### 0x10 `CMD_CAL_GET` — 读标定参数

**需求 1 的"标定值/是否标定"。** 参数：无。任意模式可用。

响应 DATA，共 **26 字节**（2 帧）：

| 偏移 | 长 | 字段 | 说明 |
|---|---|---|---|
| 0 | 12 | `cal_zero[3]` | int32 × 3，三通道零点 |
| 12 | 12 | `cal_k[3]` | **float32 × 3**，联合标定系数 |
| 24 | 1 | `cal_epoch` | 标定世代号 |
| 25 | 1 | `calibrated` | 0/1，等价于 `cal_k` 不全为 0 |

标定模型（与 `app_storage_weight_calc()` 及 `_solve.py` 一致）：

```
W = k0·(x0 − z0) + k1·(x1 − z1) + k2·(x2 − z2)
```

> ⚠ **这是三通道联合模型，不是逐通道增益。** `k_i` 是最小二乘解出的权重，
> 实测有一个是**负数**（真实数据 `k2 = −2.555e-03`）。客户端不要对 `k` 的符号
> 或量级做假设，也不要试图单独用某个 `k_i` 去换算单通道重量。
>
> ⚠ 处于标定模式时，本命令返回的是 **RAM 工作副本**（可能含未提交的改动）；
> 不在标定模式时返回的就是 flash 里的值。客户端靠 `INFO.flags.CFG_DIRTY` 区分。

### 0x11 `CMD_CAL_ENTER` — 进入标定模式

参数（帧长 4）：

| 偏移 | 长 | 字段 | 说明 |
|---|---|---|---|
| 0 | 2 | `timeout_s` | 看门狗超时秒数，**0 = 用默认 300**；有效 30..3600 |

响应 DATA：2 字节 = 生效的 `timeout_s`。

已在标定模式时重复调用 → `ERR_WRONG_MODE`（不静默成功，避免客户端以为超时被刷新了；
要续期请用 `CAL_ENTER` 前先 `CAL_EXIT`，或由 §11 建议 F 决定加一条续期命令）。

进入后设备行为变化见 §6。

### 0x12 `CMD_CAL_EXIT` — 退出标定模式

参数（帧长 3）：

| 偏移 | 长 | 字段 | 说明 |
|---|---|---|---|
| 0 | 1 | `save` | 0 = **丢弃**未提交的改动；1 = 提交到 flash（等价于先 `CFG_SAVE`） |

响应 DATA：1 字节 = 实际是否写了 flash（0/1）。

`save=1` 而标定参数非法（§7.2 校验）→ `ERR_BAD_PARAM`，**且不退出模式**，
让客户端有机会改正。

设备也会在这三种情况下**自行退出**（等价于 `save=0`）：

1. 标定模式看门狗超时 → 主动推 `0x12|0x80, TAG=0xFF`；
2. 连接断开；
3. 收到 `REC_ERASE`（语义冲突，见 §6）。

### 0x13 `CMD_CAL_ZERO_SET` — 写零点

**须在标定模式**，否则 `ERR_WRONG_MODE`。参数（帧长 3 或 15）：

| 偏移 | 长 | 字段 | 说明 |
|---|---|---|---|
| 0 | 1 | `mode` | 0 = **取设备当前三通道滑动平均**作为零点（帧长 3）<br>1 = 用下面给定的值（帧长 15） |
| 1 | 12 | `zero[3]` | int32 × 3，仅 `mode=1` 时存在 |

响应 DATA：12 字节 = 实际生效的 `zero[3]`（`mode=0` 时客户端据此知道取到了什么）。

`mode=0` 且当前数据不是 `STABLE` → **仍然执行，但响应 `STATUS=OK`**，
客户端应自行先确认 `SENSOR.flags.STABLE` 再调用。

> **为什么 `mode=0` 不强制要求 STABLE**：空秤零点的稳定判定偶发抖动时会一直取不到，
> 强制会让操作卡住。把判断权交给客户端（它有 `SENSOR` 可看），
> 与固件"记录不因不稳定而拒写、靠 flags 自证"的既有取舍一致。

**只改 RAM 工作副本，不落盘**（见 §7.1）。

### 0x14 `CMD_CAL_K_SET` — 写最小二乘系数

**须在标定模式**。参数（帧长 14）：

| 偏移 | 长 | 字段 | 说明 |
|---|---|---|---|
| 0 | 12 | `k[3]` | **float32 × 3**，IEEE754 小端 |

响应 DATA：无（帧长 4）。

固件校验：任一 `k_i` 为 NaN / Inf → `ERR_BAD_PARAM`。
**允许负数与 0**（负数是实测事实，全 0 表示"标为未标定"）。

**只改 RAM 工作副本，不落盘。** 改完立即生效 —— 客户端可马上用
`CMD_SENSOR` 看新系数算出来的重量对不对，不满意就再下发一组，
全程不碰 flash。

### 0x20 `CMD_CFG_SET` — 改配置

任意模式可用。参数（帧长 4 ~ 13）：

| 偏移 | 长 | 字段 | 说明 |
|---|---|---|---|
| 0 | 2 | `mask` | 位掩码，选择本次要改哪些字段 |
| 2 | … | 值 | 按 `mask` 中置位的字段，**按位号从低到高依次紧密排列** |

| 位 | 字段 | 类型 | 范围 |
|---|---|---|---|
| 0 | `drink_idx` | u8 | `< drink_count` |
| 1 | `drink_count` | u8 | 1..16 |
| 2 | `adv_events` | u16 | ≥ 1 |
| 3 | `adv_interval_ms` | u16 | 20..10240 |
| 4 | `present_thr_g` | i16 | 1..2000，单位克（新增字段） |

响应 DATA：无。

同时改 `drink_count` 与 `drink_idx` 时，固件按**改完之后的值**统一校验
（`drink_idx < drink_count`），避免"先设 idx 再设 count"的中间态被拒。

**只改 RAM 工作副本，不落盘。**

> ⚠ `mask` 的紧密排列意味着长度可变，固件必须按 `mask` 算出期望长度再校验，
> 不符回 `ERR_BAD_LENGTH`。这比"每个字段一条命令"省往返，比"固定全量结构"
> 省字节，代价是解析要写一段位遍历。

### 0x2F `CMD_CFG_SAVE` — 提交到 flash

任意模式可用。参数：无。

响应 DATA：1 字节 = 新的 `cal_epoch`。

行为：把 RAM 工作副本整体写入配置页（`app_storage_cfg_save()`：先校验 → 擦一页 → 写）。
若本次提交改动了 `cal_zero` 或 `cal_k`，则 `cal_epoch` 先 +1 再写。

校验不过 → `ERR_BAD_PARAM`，**不擦不写**（`app_storage_cfg_save()` 已经是这个顺序）。
fstorage 失败 → `ERR_STORAGE`。

**阻塞约 90~180ms**（擦一页 87ms + 写）。客户端超时给 3s。

> ### 为什么所有写命令都是"改 RAM + 显式提交"，而不是逐条落盘
>
> 1. **flash 寿命**：配置页 10000 次擦写。标定是个试错过程 —— 上位机放几组砝码、
>    解一次方程、下发一组 `k`、看重量对不对、不对就调整再下发。一次完整标定可能
>    下发十几次。逐条落盘的话，几百次标定就吃掉可观的寿命份额。
> 2. **实时可见**：RAM 改完立即参与 `weight_calc`，客户端能马上看到效果；
>    落盘反而不影响计算结果，纯粹是持久化动作。
> 3. **原子性**：`app_storage_cfg_t` 是**一个结构、一次整页重写**。
>    如果 `CAL_K_SET` 与 `CFG_SET` 各自落盘，后者会把前者尚未定稿的标定值
>    一起写进去 —— 语义混乱。统一到一个提交点就没有这个问题。
> 4. **代价**：断电/断连会丢未提交的改动。这是有意的 —— 标定没做完就断，
>    本来就不该留下半套系数。`INFO.flags.CFG_DIRTY` 让客户端随时能提醒用户。

### 0x30 `CMD_REC_READ` — 分页下载记录

**需求 5 的落地。** 任意模式可用。参数（帧长 5）：

| 偏移 | 长 | 字段 | 说明 |
|---|---|---|---|
| 0 | 2 | `idx` | 起始索引，**0 = 最新一条**（与 `app_storage_rec_get()` 同向） |
| 1 | 1 | `count` | 请求条数，1..**64** |

响应 DATA：`1 + n × 20` 字节

| 偏移 | 长 | 字段 |
|---|---|---|
| 0 | 1 | `n` — 实际返回条数，可能 < `count`（读到末尾） |
| 1 | 20×n | 记录流，每条 20 字节，格式见 §7.4 |

- `idx >= rec_count` → `ERR_NOT_FOUND`；
- `count = 0` 或 `> 64` → `ERR_BAD_PARAM`；
- `n = 0` 不会出现（`idx` 合法就至少有 1 条）；
- `count=64` 时 DATA = 1281 字节 = **81 帧**，在 128 帧上限内。

**全量下载流程**：读 `INFO.rec_count` → 从 `idx=0` 起以 32 或 64 为步长循环，
直到累计条数达到 `rec_count`。

> ⚠ **下载期间不保证快照一致性。** 若此刻有人按键存了新记录，索引会整体后移一位，
> 客户端可能重复拿到一条或漏掉一条。三种应对，本协议选第 3 种：
> 1. 设备端加锁禁止写入 —— 会丢用户按键，不可接受；
> 2. 设备端做快照 —— 需要 12KB RAM，nRF52810 只有 24KB，不可能；
> 3. **客户端用 `seq` 去重**：`seq` 是全局单调递增的（`app_storage.c` 的
>    `m_next_seq`），客户端按 `seq` 建索引即可，重复的丢掉、缺的下一轮补。
>    这也顺带支持断点续传与增量下载。
>
> ⚠ **只返回原始计数，不返回算好的重量。** 理由：重量依赖标定参数，而标定参数
> 会变。返回 raw 让客户端能在标定更新后**重算全部历史数据**；返回算好的值则
> 历史数据永远钉死在采集时那套系数上。记录里的 `cal_epoch`（§7.3）告诉客户端
> 每条记录是哪套系数采的，从而能判断"这条要不要重算"。

---

### 0x31 `CMD_REC_ERASE` — 清空全部记录

**需求 5 的落地。** 任意模式可用（但会强制退出标定模式，见下）。参数（帧长 6）：

| 偏移 | 长 | 字段 | 说明 |
|---|---|---|---|
| 0 | 4 | `confirm` | 必须等于 **0x53415245**（ASCII `'ERAS'` 小端） |

响应 DATA：无。`confirm` 不符 → `ERR_CONFIRM`，**不擦任何东西**。

行为：`app_storage_rec_erase_all()`，擦 3 页，**阻塞约 260ms**，
然后 `rec_count`/`seq` 全部归零。客户端超时给 3s。

- 处于标定模式时收到本命令 → **先自动退出标定模式（丢弃未提交改动），再执行擦除**。
  理由：标定模式的语义是"停止记录数据"，而擦除是记录区的重大操作，
  两者叠加的状态没人能说清；强制收敛到一个明确状态。
  响应仍是 `REC_ERASE` 的，同时另发一帧 `0x12|0x80, TAG=0xFF` 告知模式变化。

> **为什么要确认码**：这是唯一一条会不可逆销毁用户数据的命令，而通道无鉴权、
> 无加密（§4 规则 5）。一个错位的字节或客户端 bug 就能擦掉 612 条记录。
> 4 字节确认码把误触发概率降到 2⁻³²，成本是每次多发 4 字节。
> `seq` **不会**因为擦除而重置到 0 之前的值……实际上会归零 —— 客户端因此
> 必须能容忍 `seq` 回退（把它当成"换了一批数据"，清空本地缓存）。

## 6. 设备模式与标定模式的副作用

### 6.1 两个模式

| | 普通模式 | 标定模式 |
|---|---|---|
| 单击按键 | LED 闪 + 播数据广播 + 存一条记录 | **LED 闪一下，其余全部抑制**（不播、不存） |
| 长按按键 | 开可连接窗口 | 同（已连接时无意义） |
| 双击按键 | 关窗口 / 断开 | 同（保留退路，见下） |
| 数据广播 | 单击触发 | **完全抑制** |
| 记录写入 | 单击时写一条 | **完全抑制** |
| HX711 采样 | 正常 100ms 节拍 | **正常，不受影响** |
| 标定参数 | 用 flash 里的值 | 用 RAM 工作副本（可含未提交改动） |

**需求 4 的落地。** 三点要说清：

1. **"停止广播"指的是数据广播（`ble_beacon`）**，不含可连接广播。
   可连接广播必须留着 —— 否则断连后就再也连不上，只能靠物理长按。
   实际上连接建立后可连接广播已由协议栈自动停止（`ble_adv_mux` 在优先级 1
   同步了状态），所以标定模式真正要拦的是"单击 → `adv_policy_burst_data()`"这条路径。
2. **单击仍然闪一下 LED。** 完全没反应会让人以为设备挂了；闪灯表示
   "收到了，但当前模式不干这个"。
3. **双击/长按行为不变。** 标定模式下必须保留一条不依赖蓝牙的退路 ——
   万一上位机崩了，用户还能双击断开连接（触发断连 → 自动退出标定模式）。

### 6.2 看门狗超时是必须的

**这是本设计里最重要的一条防呆。** 标定模式下设备既不广播也不记录 ——
如果上位机崩溃、跑掉、或忘了退出，设备就变成一块"通电但什么也不做"的板子，
而且**从外部完全看不出来**（平时本来就静默，见 `main.c` 的 `adv_policy_*`）。
用户会以为设备坏了。

因此：

- `CAL_ENTER` 必须带超时，默认 **300 秒**，范围 30..3600；
- 超时到达 → 自动 `CAL_EXIT(save=0)` + 主动推一帧告知；
- **断连也立即退出**（比超时更快，覆盖上位机崩溃的常见情况）；
- 建议固件在标定模式下让 LED **慢闪**（`DRV_LED_BLINK_SLOW`），
  给一个外部可见的状态指示 —— 快闪已被"可连接窗口"占用，常亮被"已连接"占用，
  慢闪空着正好。

## 7. 数据结构与固件对应关系

### 7.1 配置的 RAM 工作副本

固件当前只有一份 `static app_storage_cfg_t m_cfg`（`main.c`），开机由
`app_storage_cfg_load()` 填充。本协议把它当作**工作副本**：

```
flash 配置页  ──load──▶  m_cfg (RAM)  ──▶ weight_calc / 广播 / 记录
                            ▲                    
                            │ CAL_*_SET / CFG_SET 直接改这里(立即生效)
                            │
                         CFG_SAVE ──save──▶ flash 配置页
```

需要新增一个 `m_cfg_dirty` 标志（对应 `INFO.flags.CFG_DIRTY`）。

### 7.2 `app_storage_cfg_t` 需要扩展（cfg v2 → v3）

现状 36 字节。本协议需要两个新字段：

| 新字段 | 类型 | 用途 |
|---|---|---|
| `present_thr_g` | `int16_t` | `PRESENT` 位的判定阈值，默认 **5** 克 |
| `cal_epoch` | `uint8_t` | 标定世代号，`CFG_SAVE` 改了标定就 +1 |
| （填充） | `uint8_t` | 保持 4 字节对齐 |

→ 40 字节，仍满足 `% 4 == 0`。

⚠ 按 `app_storage.h` 自己写明的规则：**加字段只能往尾部加，并递增
`APP_STORAGE_CFG_VERSION`（2 → 3）**。老设备升级后 version 不匹配 →
`cfg_load()` 回退默认值，**标定参数会丢，需要重新标定**。这是有意的保守行为，
但**升级前要提醒用户先用 `CAL_GET` 把系数抄下来**。

`present_thr_g` 默认 5 克的理由：噪声底噪 ±30 counts ≈ 0.08 g，
最不灵敏的 ch1 是 49.3 counts/g；5 克远高于噪声，又远低于任何真实杯子的重量。

### 7.3 `flags` 字段的统一布局（16 位）

`CMD_SENSOR` 的 `flags`、`app_storage_rec_t.flags`、以及广播协议里的数据状态位
**共用低 8 位定义**，避免三处各写一套：

| 位 | 名称 | 定义于 |
|---|---|---|
| 0 | `STABLE` | `app_proto.h`（已有） |
| 1 | `SETTLING` | `app_proto.h`（已有） |
| 2 | `STALE` | `app_proto.h`（已有） |
| 3 | `UNCAL` | `app_proto.h`（已有） |
| 4 | `PRESENT` | **本协议新增** |
| 5..7 | 保留 | 必须为 0 |
| 8..15 | `cal_epoch` | **本协议新增**：写记录时的标定世代号 |

> **把 `cal_epoch` 塞进 `flags` 高 8 位而不是新增字段**：`app_storage_rec_t`
> 现在正好 20 字节，加字段就要改记录大小 → `RECS_PER_PAGE` 变化 → 老数据全部
> 错位无法读。而 `flags` 是 `uint16_t` 且只用了 4 位，高 8 位白放着。
> 零成本解决"这条记录是哪套系数采的"这个问题。

### 7.4 记录的线路格式（20 字节，与 `app_storage_rec_t` 逐字节一致）

| 偏移 | 长 | 字段 | 说明 |
|---|---|---|---|
| 0 | 4 | `seq` | u32，全局单调递增；`0xFFFFFFFF` 不会出现（那是空槽标志） |
| 4 | 2 | `batt_mv` | u16，电池电压 mV |
| 6 | 2 | `flags` | 见 §7.3 |
| 8 | 12 | `ch[3]` | int32 × 3，三通道原始计数（已符号扩展的 24bit） |

固件可以直接 `memcpy` 结构体上线路，无需逐字段打包 —— 这是刻意让线路格式
等于内存布局的收益。

⚠ **但有一个必须先修的 bug**：`main.c` 的 `adv_policy_burst_data()` 里
`m_store_snap.batt_mv = saadc_sample_channel(...)` 存的是 **ADC 原始计数**，
没过 `saadc_raw_to_mv()`。所以现在 flash 里的 `batt_mv` 字段是 raw（3.0V 时约 3413，
恰好"看起来像"毫伏值，因此一直没被发现）。本协议直接把这个字段当 mV 上报，
**实现前必须修掉**，否则已有记录与新记录的语义不一致。

## 8. 标定作业流程（客户端实现参考）

这是协议的主要使用场景，也是核对协议是否够用的最佳检验。

```
 1. 长按按键 → 30s 可连接窗口 → 连接 → 使能 TX 通知
 2. CMD_INFO                      拿版本号、是否已标定、cal_epoch
 3. CMD_CAL_GET                   抄下现有系数（万一要回滚 / 或升级前备份）
 4. CMD_CAL_ENTER(timeout=600)    进标定模式（设备停播、停记录、LED 慢闪）
 5. CMD_SENSOR_STREAM(200)        开推流，界面上实时显示三通道与重量
 6. 清空秤台
    等 flags.STABLE
    CMD_CAL_ZERO_SET(mode=0)      取当前滑动平均作为零点 z[]
 7. 对每个已知砝码 m_j (至少 3 个，建议 4~6 个覆盖量程):
       放上砝码
       等 flags.STABLE
       记下 (x0,x1,x2) 与 m_j
 8. 上位机解线性方程组求 k[]:
       [x0-z0  x1-z1  x2-z2]_j · k = m_j
       3 组样本 → 恰定，直接解（见 dev/app/sensor_beacon/_solve.py）
       >3 组    → 超定，最小二乘
 9. CMD_CAL_K_SET(k[])            下发，立即生效（仍在 RAM）
10. 复核: 放一个未参与拟合的砝码 → CMD_SENSOR → 看 weight_g 误差
       不满意 → 回第 7 步补样本，重解，重下发（不碰 flash）
11. CMD_CFG_SET(mask=present_thr_g, ...)   顺便设放置阈值
12. CMD_CAL_EXIT(save=1)          提交到 flash，cal_epoch +1，退出标定模式
13. CMD_SENSOR_STREAM(0)          关推流
14. 双击按键 或 断开连接
```

⚠ **第 7 步为什么至少 3 个砝码**：模型有 3 个未知数 `k0/k1/k2`。
`_solve.py` 里那组真实数据就是 3 个砝码（200/300/400 g）恰定求解。
只放 1~2 个砝码方程欠定，解出来的 `k` 是任意的。

⚠ **砝码要覆盖量程且互不成比例**。三个砝码若读数近似成比例，
矩阵接近奇异，解出的 `k` 会被噪声放大到毫无意义。上位机应检查条件数并给警告。

## 11. 检查出的疏漏与建议

按重要性排序。标 **【建议】** 的是我的推荐做法，标 **【待决】** 的需要拍板。

### 疏漏 1 —— "是否有放置物体"当前固件完全没有这个概念 【建议】

需求 2 要求返回它，但代码里没有任何"放置检测"。它需要：

- 一个阈值（新增配置字段 `present_thr_g`，§7.2）；
- 一个判据。**建议 `|weight_g| >= present_thr_g`，不要求 STABLE** ——
  刚放上就该报"有物体"，而稳定要等 2~3 秒；
- 未标定时该位无意义（`weight_g` 恒为 0）→ 固件应置 `UNCAL` 并把 `PRESENT` 清 0。

⚠ 用 `|weight|` 的绝对值而不是 `weight > thr`：负重量是真实存在的
（杯子被拿走后零点漂移、或标定零点是带杯的），只判正会漏掉。

### 疏漏 2 —— 饮料类型只有"数量"和"索引"，没有名字/密度 【待决】

配置区只存 `drink_count` 和 `drink_idx`，广播包只有 4 位类型号。
那么界面上"矿泉水/茶/咖啡"这些名字从哪来？两条路：

- **A（建议）**：名字表放在上位机，设备只认索引。零固件成本，改名字不用动设备。
  缺点是换手机/换客户端要重新配一遍。
- **B**：设备存名字。16 种 × 8 字节 = 128 字节，配置页放得下，但要加
  `CMD_DRINK_GET/SET` 两条命令和一套字符串编码（UTF-8 截断问题）。

如果饮水量要按饮料密度换算（体积 vs 重量），密度系数也有同样的归属问题。
**本协议 v1 按 A 设计** —— 若选 B 需要加命令，属 v2。

### 疏漏 3 —— "协议版本号"实际上有四个，需求里只提了一个 【建议】

见 §10。`INFO` 一次全给，客户端才能同时正确解广播包和命令帧。
只给一个版本号会导致：客户端认得命令协议 v1，却按错误的布局解广播包。

### 疏漏 4 —— 标定模式没有超时会把设备变"砖" 【建议·重要】

见 §6.2。标定模式下设备不广播不记录，而平时本来就静默 —— **外部无法区分
"在标定模式"和"设备坏了"**。必须有看门狗超时 + 断连自动退出 + LED 慢闪指示。
这是我认为整个设计里最容易被忽略、后果最尴尬的一条。

### 疏漏 5 —— 传感器数据的可信度标志必须返回，需求里没提 【建议】

见 `CMD_SENSOR` 的说明。没有 `STABLE/SETTLING/STALE`，标定流程只能盲等，
采到震荡期读数会解出偏差几十克的系数。`sample_tick` 同理 —— 没有它无法区分
"读到同一帧"与"值真的没变"。

### 疏漏 6 —— 发送流控缺失，下载功能会丢帧 【建议·必做】

见 §1.4。`ble_link_send()` 现在遇到 `NRF_ERROR_RESOURCES` 就丢数据。
`REC_READ` 一次连发几十帧，必丢。**必须实现 TX 队列 + `BLE_NUS_EVT_TX_RDY`
驱动续发**（该事件分支已存在，是空的）。这是固件侧最大的一块新增工作。

### 疏漏 7 —— 重置存储没有防误触保护 【建议】

无鉴权无加密的通道上，一条 2 字节的命令就能不可逆销毁 612 条记录。
已加 4 字节确认码（§`REC_ERASE`）。同时客户端界面应有二次确认。

### 疏漏 8 —— 下载期间的一致性 【建议】

见 `REC_READ` 的说明。选"客户端按 `seq` 去重"，因为设备端加锁会丢用户按键、
做快照要 12KB RAM（芯片总共只有 24KB）。副作用是顺带获得断点续传与增量下载。

### 疏漏 9 —— 历史记录的重量含义会随标定改变 【建议】

标定参数改了以后，旧记录该用哪套系数算？加了 `cal_epoch`（§7.3），
塞进 `flags` 高 8 位，零成本。客户端据此知道哪些记录需要用哪套系数、
或提示"这批数据是旧标定采的"。

### 疏漏 10 —— 通道完全无鉴权 【待决，建议接受现状】

`ble_link.c` 的 `BLE_GAP_EVT_SEC_PARAMS_REQUEST` 分支明确回
`PAIRING_NOT_SUPP`，注释里也写了"现在任何人连上就能发命令"。
本协议引入了破坏性操作（改标定、擦记录），风险实际上升了。

**建议接受现状，不加密码**，理由：

1. 可连接广播**只能靠物理长按按键**打开，窗口 30 秒；
2. S112 只有 1 个连接槽，连上后窗口即关闭，别人插不进来；
3. 即"能连上"已经等价于"人在设备旁边并按过按键"，这是相当强的在场证明；
4. 加共享密钥会带来密钥烧写、丢失恢复、明文传输（无加密下密钥本身会被嗅探）
   等一串新问题，收益却只覆盖"有人在你按键那 30 秒里抢先连上"这个极窄场景。

**但若日后需求变成"可连接窗口常开"或"远程配置"，必须补鉴权** ——
届时应直接上 BLE 配对 + 加密（`peer_manager`），而不是自己发明认证协议。

### 疏漏 11 —— `batt_mv` 存的是 ADC 原始值 【必修 bug】

见 §7.4 末尾。`main.c:857` 漏了 `saadc_raw_to_mv()` 换算。
实现本协议前必须修，否则新旧记录语义不一致，而且这个 bug 很隐蔽
（raw 3413 看起来就像 3413 mV）。

### 疏漏 12 —— 广播参数可改，但改了不生效 【待决】

`app_storage_cfg_t` 有 `adv_events` / `adv_interval_ms`，`CFG_SET` 也能改它们，
**但固件目前根本没读这两个字段** —— `ble_beacon.c` 用的是编译期常量
`BLE_BEACON_ADV_EVENTS` / `BLE_BEACON_ADV_INTERVAL_MS`。

两条路：**A（建议）** 让 `ble_beacon` 读配置（加一个 `ble_beacon_set_params()`），
或 **B** 从 `CFG_SET` 的 mask 里删掉这两位，避免"设了没用"的假象。
选 A 要注意 `sd_ble_gap_adv_set_configure()` 在广播中不能改参数，
所以只能在下一轮 burst 生效。

### 建议 F —— 标定模式续期命令（可选，v1 暂不做）

超时 300s 对慢工细活的标定可能不够。当前解法是 `CAL_ENTER(timeout=3600)` 一次给足。
若实测发现不够灵活，v2 可加一条 `CMD_CAL_KEEPALIVE`。**v1 先不加**，
避免为一个尚未出现的问题加接口。

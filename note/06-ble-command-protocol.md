# 06 · BLE 连接态命令协议 (cmd proto v1)

设备**被连接之后**，经 NUS 透传通道收发的请求/响应协议。供上位机（`dev/desktop/index.html`）、
手机 App 与固件三方对照实现。

> **本文只写协议本身** —— 帧格式、命令码、字段偏移、状态码、会话规则，供开发直接查询。
> 设计依据、被否掉的方案、固件实现陷阱、遗留问题与待办清单一律在
> [`07-cmd-protocol-design-notes.md`](07-cmd-protocol-design-notes.md)（下称 **07**）。
>
> ⚠ 本文是**领先于代码的规范**：截至撰写时固件侧尚未实现任何一条命令
> （`nus_data_handler` 只做 hexdump + 原样回显）。实现时以本文为准；发现不符请改本文，
> 而不是改代码注释。所有常量最终应收敛到一个 `services/cmd_proto.h` 里供双方共用。

---

## 0. 与广播协议的边界（先划清，免得混淆）

设备上有**两套完全独立的协议**，各有各的版本号，互不影响：

| | 广播协议 | 命令协议（本文） |
|---|---|---|
| 载体 | 不可连接广播的厂商自定义段 | 连接后的 NUS 特性（Write / Notify） |
| 方向 | 单向，设备 → 空气（pc等上位机采集） | 双向，请求 / 响应 |
| 触发 | 正式:用户放杯，设备读数稳定后自行触发；调试：单击按键 → 播 `BLE_BEACON_ADV_EVENTS` 次 | 长按开 30s 窗口 → 连上 → 随时发命令 |
| 字节预算 | **31 字节硬上限**（BLE 4.x 传统广播） | 下行 20 字节/帧；上行按协商 MTU（最多 244 字节/帧）<br>（方向定义见 §2.0：**下行 = 上位机 → 设备**） |
| 定义位置 | `services/app_proto.h`、note 05 | `services/cmd_proto.h`（待建）、本文 |
| 版本号 | `APP_PROTO_VERSION`（现 0x02，v3 已设计未接线） | `CMD_PROTO_VERSION` = 1 |

**本协议不改动广播包的任何一个字节。** 两者唯一的交集是：

1. **蓝牙连接后会抑制数据广播的"触发"**（§6）—— 抑制的是"什么时候播"，
   播出去的包格式仍然完全由广播协议决定。
2. `CMD_INFO` 会**同时报告两个版本号**，让上位机一次拿到"该按哪套规则解广播包、
   该按哪套规则发命令"。

⚠ 另一处容易混淆的地方：广播协议 v3 里也有"记录"概念（8 条 × 2 字节 = 类型 + 克数），
那是**为了塞进 31 字节而极度压缩的摘要**；本协议 `CMD_REC_READ` 下载的是
**完整原始记录**（20 字节 / 条，含三通道原始计数）。同名不同物，不要互相套用。

## 速览：一次完整的问答长什么样

先用一次真实交互把协议的形状讲完，后面各节都是这张图的细节。

### 两个角色

本文一律用「上位机」和「设备」这两个词，不用"主/从"——蓝牙里 master/slave 另有
含义（指链路层角色），混用会越说越糊。

| 角色 | 是谁 | 能做什么 |
|---|---|---|
| **上位机** | PC 工具（`sensor_tool`）、手机 App | **只有它能发起请求** |
| **设备** | nRF52810 固件 | 只应答；外加两种主动上报（§2.4） |

### 一次问答：读一次传感器

下面这张图用**最保守的连接（ATT MTU 23）**举例，所以 26 字节的响应要拆成 2 帧；
MTU 247 下同一条响应只有 1 帧（§1.2 / §2.3）。

上位机发 2 个字节，设备回 2 帧：

```
REQUEST  上位机 -> 设备
  02 07
  |  |
  |  +----- TAG    = 0x07              上位机自编的流水号，设备原样回填
  +-------- CMD    = 0x02 (CMD_SENSOR) 这条命令没有参数，所以整帧就 2 字节

RESPONSE frame 0  设备 -> 上位机
  82 07 00 80  + 16 bytes DATA
  |  |  |  |
  |  |  |  +-- FRAG   = 0x80            bit7=1 还有后续帧；帧号 = 0
  |  |  +----- STATUS = 0x00            成功
  |  +-------- TAG    = 0x07            原样回填，上位机据此认出
  |                                     "这是我那条请求的应答"
  +----------- CMD    = 0x02|0x80 =0x82 最高位 = 1 表示这是应答

RESPONSE frame 1  设备 -> 上位机
  82 07 00 01  + 10 bytes DATA
           |
           +-- FRAG   = 0x01            bit7=0 这是最后一帧；帧号 = 1
```

> ⚠ 上面这种图里，竖线左边一律只用 ASCII，中文只出现在行尾 —— 中文是双宽字符，
> 混进对齐区会让任何等宽渲染下的箭头都对不上。以后加图请守这条。

上位机把两帧的 DATA 按帧号拼起来，得到 16 + 10 = 26 字节，**然后**才按
`CMD_SENSOR` 的字段表（§5）去解。帧本身只管搬运，不认识里面装的是什么。

### 时序

| 步 | 谁 → 谁 | 干什么 | 说明 |
|---|---|---|---|
| ① | **人** → 设备 | 长按设备按键 | 设备开 30 秒可连接窗口 |
| ② | 上位机 → 设备 | 连接，并使能 TX 通知 | 漏了"使能通知"就收不到任何响应（§1.1） |
| ③ | 上位机 → 设备 | `write(02 07)` | 设备：查命令码 → 查长度 → 执行（§4.2） |
| ④ | 设备 → 上位机 | `notify(82 07 00 80 …)` | 第 0 帧，MORE=1 |
| ⑤ | 设备 → 上位机 | `notify(82 07 00 01 …)` | 第 1 帧，MORE=0 → **本次问答结束** |
| ⑥ | 上位机 → 设备 | 下一条请求… | 必须等第 ⑤ 步收完，否则回 `ERR_BUSY`（§4.1） |

⚠ 第 ① 步是**人**的动作，绕不过去：可连接广播只有 30 秒窗口，而且只能靠物理
长按打开。所以上位机**做不了自动重连**——"记住设备 → 后台重连 → 掉线自动恢复"
那套标准套路在这个设备上全部失效，UI 必须围绕"请去按住按键"来设计。

✅ **已定稿：设备会在空闲时主动断开连接**，默认 **300 秒**，可用 `CMD_LINK_IDLE`
改或关闭（`0` = 关闭），详见 §4.6。这条规则同样是"人"这一侧的单点 —— 手机被
放着不管时，设备必须能自己收摊，否则会一直占着唯一的连接槽。

### 记住这五条就够了

1. **只有上位机能提问。** 设备不会无故说话——例外只有 §2.4 的两种主动上报。
2. **一问一答，不许并发。** 上一条还没答完就问下一条 → 设备回 `ERR_BUSY`（§4.1）。
3. **每条请求必有应答。** 哪怕失败也回一帧，`STATUS` 说明原因（§2.2）。
4. **帧只是搬运工。** 长数据切成多帧，拼完再解结构（§2.3）。
5. **设备会自己收摊。** 连续 300 秒没有请求就主动断开（§4.6），客户端要按"随时可能掉线"来设计。

## 1. 传输层与硬约束

### 1.1 走哪条通道

用 Nordic UART Service（NUS），128bit 厂商 UUID。固件侧 `ble_link.c` 已经实现，
这一层不需要改动：

| 特性 | UUID | 方向 | 装什么 | 怎么用 |
|---|---|---|---|---|
| Service | `6e400001-b5a3-f393-e0a9-e50e24dcca9e` | — | — | — |
| RX | `6e400002-…` | 上位机 → 设备 | **请求帧** | Write / Write Without Response |
| TX | `6e400003-…` | 设备 → 上位机 | **响应帧** | Notify |

名字里带 UART 只是因为它最早用来做串口透传，本协议并没有把它当串口用——**它是
有明确帧边界的**，见 §1.3。

**用之前必须做完三件事**，缺一件都收不到东西：

1. 长按设备按键，打开 30 秒可连接窗口（`BLE_LINK_ADV_DURATION_MS`）；
2. 连上；
3. **使能 TX 特性的通知**（`startNotifications` / 订阅）。

⚠ 第 3 步最容易漏。没使能通知时设备侧 `ble_link_send()` 直接返回
`NRF_ERROR_INVALID_STATE`——**响应发不出来，而请求是能正常写进去的**。表现就是
"命令好像执行了但什么都没回"，很费时间。

### 1.2 每帧长度上限

| 方向 | 每帧上限 | 谁决定 |
|---|---|---|
| **下行**（请求，上位机 → 设备） | **20 字节，固定** | 协议规定 |
| **上行**（响应 / 主动上报，设备 → 上位机） | `min(240, eff_mtu − 7)` | **设备**运行时算 |

上行每帧的 `DATA` 长度因此是**运行时变量**：

```
每次通知长度    ≤ eff_mtu − 3     （ATT 头开销）
每帧 DATA 长度  ≤ eff_mtu − 7     （再减 4 字节帧头 CMD|TAG|STATUS|FRAG）
MTU 247 时      → 每帧 240 字节数据（MTU 23 时是 16）
```

**对实现的两条硬要求**：

1. 客户端发请求永远 ≤ 20 字节，**不得**根据 `INFO.eff_mtu` 加长请求帧
   （客户端拿不到协商后的 MTU，20 是唯一安全值）。
2. 客户端解析响应时**不要假设"每帧 16 字节"** —— 丢帧检测只能靠帧号连续性（§2.3）。

> 两个数字的推导、为什么不做 MTU 探测握手，见 07 §1.1–1.3。


### 1.3 帧边界

帧边界由 GATT 保证：上位机一次 `write`，到固件就是**一个** `BLE_NUS_EVT_RX_DATA`
事件，长度精确；超 MTU 的长写由 `nrf_ble_qwr` 重组后**仍然作为一个事件**投递。

**因此协议里没有 magic、没有长度字段、没有 CRC。** 由此得出一条对客户端的硬性
要求：**一条命令必须在一次 write 里整帧发出，不许自己分片** —— 分片会被固件当成
两条残帧解析（回 `ERR_BAD_LENGTH`）。请求帧 ≤ 20 字节，这一点天然成立。

> 为什么这三样都可以省，见 07 §1.4。

### 1.4 固件实现前提（两条，缺一协议就跑不起来）

| 前提 | 不满足的后果 |
|---|---|
| 收到请求**入队到主循环**执行，不能在 SoftDevice 事件中断里就地处理 | 访问 flash 时死锁 |
| 发送必须有**队列 + `BLE_NUS_EVT_TX_RDY` 驱动续发** | 多帧响应必然丢帧 |

细节见 07 §4.1 / §4.2，吞吐估算见 07 §5。

## 2. 帧格式

全协议**小端**，与固件结构体的内存布局一致，两侧都不需要做字节序转换。

### 2.0 术语：上行 / 下行（以设备为参照，与 NUS 的 TX/RX 一致）

**本文一律以「设备」为参照点**，与串口/BLE 模块的 `TX`/`RX` 习惯一致：

| 本文用词 | 方向 | 载体 | 帧类型 | 长度上限 |
|---|---|---|---|---|
| **下行** | 上位机 → 设备 | NUS `6e400002`（**RX** 特性，Write） | 请求帧（§2.1） | **20 字节**（钉死） |
| **上行** | 设备 → 上位机 | NUS `6e400003`（**TX** 特性，Notify） | 响应帧 / 主动上报（§2.2、§2.4） | 设备按协商 MTU 自算 |

一句话记法：**"上行 = 设备说，下行 = 对设备说"**。
（为什么这样定、以及早期"客户端视角"的写法为何废弃，见 07 §0。）

⚠ 两个方向的长度上限不同：**下行 20 字节固定，上行按协商 MTU**，见 §1.2。

### 2.1 请求帧：上位机 → 设备，2 ~ 20 字节

```
 偏移  长度  字段
 ----  ----  ------------------------------------------------
   0     1   CMD     命令码，0x01..0x7F（0x00 与 0x80+ 非法）
   1     1   TAG     上位机自选的流水号，设备原样回填
   2     N   ARGS    命令参数，N = 0..18
```

| 字段 | 谁填 | 要注意什么 |
|---|---|---|
| `CMD` | 上位机 | 最高位必须是 0。最高位是"方向位"，置 1 就变成响应了（§2.2） |
| `TAG` | 上位机 | 建议 0x00..0xFE 循环递增。**0xFF 是保留值，客户端不得使用** |
| `ARGS` | 上位机 | 长度由命令决定，见 §5。多一个字节少一个字节都回 `ERR_BAD_LENGTH` |

**TAG 到底解决什么问题？** NUS 的通知是一条异步流，设备的主动上报（§2.4）会和
请求的应答**混在同一条流里**。没有 TAG 就会出这种事：

```
上位机 ── 发 CMD_SENSOR(TAG=7) ──> 设备
上位机 <─ 收到一帧 CMD_SENSOR 响应 ─ 这是我那条请求的应答？
                                    还是推流(§2.4)自己推上来的一帧？
```

有了 TAG 就没有歧义：`TAG=7` 是应答，`TAG=0xFF` 是主动上报。

### 2.2 响应帧：设备 → 上位机，4 ~ 244 字节

```
 偏移  长度  字段
 ----  ----  ------------------------------------------------
   0     1   CMD|0x80  对应请求的命令码，最高位置 1
   1     1   TAG       回填请求的 TAG（主动上报填 0xFF）
   2     1   STATUS    0x00 = 成功，非 0 见 §3
   3     1   FRAG      bit7    = MORE，1 表示还有后续帧
                       bit6..0 = 帧号 0..127
   4     M   DATA      数据，M = 0..DATA_MAX（随协商 MTU 变，见 §1.2）
```

`FRAG` 这一个字节要拆开看，最容易读错：

| FRAG 值 | 含义 |
|---|---|
| `0x00` | 帧号 0，且**这是最后一帧** → 单帧响应 |
| `0x80` | 帧号 0，后面还有 |
| `0x81` | 帧号 1，后面还有 |
| `0x02` | 帧号 2，**最后一帧** |

**失败的响应永远是 4 字节**：`STATUS != 0`、`FRAG = 0x00`、`DATA` 为空。
这就是需求 6"每条命令都有执行结果返回"的统一落地方式——**客户端只要看
`STATUS` 这一个字节**，不必按命令分别判断。

### 2.3 多帧响应：帧只搬运，拼完再解

响应数据超过一帧的容量（`DATA_MAX = min(240, eff_mtu − 7)`）就要拆帧。规则四条：

1. 帧号从 0 开始递增；
2. 除最后一帧外，`MORE = 1`；
3. 除最后一帧外，`DATA` 必须**填满 `DATA_MAX`**（同一响应内每帧等长）；
4. 客户端按帧号把各帧 `DATA` 拼成一段连续字节流，**然后**才按该命令的结构解析。

⚠ **丢帧检测靠帧号连续性，不靠"满 16 字节"**：客户端要求第 n 帧的帧号恰好是 n，
不连续就整轮丢弃重来。`DATA_MAX` 是随连接变化的（MTU 23 时是 16，MTU 247 时是 240），
所以**任何写死 16 的校验都是错的**；只有帧号是全连接无关的。

举例（**最保守的连接，`DATA_MAX = 16`**）：`CMD_INFO` 的 42 字节响应是 3 帧：

| 帧号 | FRAG | DATA 长度 | 说明 |
|---:|---|---:|---|
| 0 | `0x80` | 16 | MORE=1 |
| 1 | `0x81` | 16 | MORE=1 |
| 2 | `0x02` | 10 | MORE=0，最后一帧可以不满 |

拼出 16+16+10 = 42 字节，再按 §5 的 `CMD_INFO` 字段表解。
（同一条响应在 MTU 247 下只有 **1 帧**、240 字节容量，DATA 长度 42。）

**上限**：帧号占 7 位 → 最多 128 帧，容量 `128 × DATA_MAX`
（MTU 23 时 2048 字节 / MTU 247 时 30,720 字节）。

⚠ `CMD_REC_READ` 的 `count ≤ 64`（响应 1281 字节）**不再是因为 128 帧不够**
—— 它在最保守的 MTU 23 下是 81 帧（够），在 MTU 247 下只要 6 帧。限制 `count`
的理由变成了"单条响应别太大，便于重传与内存控制"，而不是帧数上限。

### 2.4 设备主动上报：TAG = 0xFF

`TAG = 0xFF` 的响应帧表示**这不是任何请求的应答**。v1 只有两处会用到：

| 场景 | 帧头 | 说明 |
|---|---|---|
| 传感器推流 | `0x82, TAG=0xFF` | 由 `CMD_SENSOR_STREAM` 开启，内容与 `CMD_SENSOR` 的响应**完全相同** |
| 强制退出标定模式 | `0x92, TAG=0xFF, STATUS=0` | 收到 `REC_ERASE` 时设备强制退出标定模式，告知上位机 |

⚠ **客户端必须能容忍在任意时刻收到 `TAG=0xFF` 帧**，包括在等某条请求的应答时。
不能把它当成上一条请求的响应——尤其是推流帧和 `CMD_SENSOR` 的应答长得一模一样，
只有 TAG 能区分。

⚠ 更隐蔽的一种错：推流帧插进一个**多帧响应的中间**。客户端的重组器必须校验
帧的 `CMD`/`TAG` 是否属于当前这一轮，不符就报错重来，不能盲目往缓冲里拼。
（`sensor_tool` 的 `proto/cmd.rs` 有一条 `detects_interleaved_frames` 专门盯这个。）

## 3. 状态码 (STATUS)

按"谁的问题"分三类看，排错时方向更明确：

**成功**

| 值 | 名称 | 含义 |
|---|---|---|
| 0x00 | `OK` | 成功 |

**客户端的问题**——改客户端代码

| 值 | 名称 | 含义 | 客户端应对 |
|---|---|---|---|
| 0x01 | `ERR_UNKNOWN_CMD` | 命令码未定义 | 检查版本号，可能是新客户端对老固件 |
| 0x02 | `ERR_BAD_LENGTH` | 请求帧长度与命令不符 | 客户端 bug |
| 0x03 | `ERR_BAD_PARAM` | 参数取值越界 | 检查参数范围 |
| 0x09 | `ERR_CONFIRM` | 破坏性操作的确认码不对 | 客户端 bug，或防误触正常生效 |

**时序/状态不对**——换个顺序再来

| 值 | 名称 | 含义 | 客户端应对 |
|---|---|---|---|
| 0x04 | `ERR_WRONG_MODE` | 该命令要求（或禁止）标定模式 | 先 `CAL_ENTER` / `CAL_EXIT` |
| 0x05 | `ERR_BUSY` | 上一条的多帧响应未发完，或 flash 操作进行中 | 等上一条完成后重试 |
| 0x07 | `ERR_NOT_FOUND` | 记录索引超出已写入条数 | 重新读 `CMD_INFO` 拿 `rec_count` |
| 0x08 | `ERR_NOT_CALIBRATED` | 需要标定参数但设备未标定 | 先完成标定 |

**设备的问题**——记日志

| 值 | 名称 | 含义 | 客户端应对 |
|---|---|---|---|
| 0x06 | `ERR_STORAGE` | fstorage 读写失败 | 重试一次；持续失败视为硬件故障 |
| 0xFF | `ERR_INTERNAL` | 不该发生的内部错误 | 上报日志 |

## 4. 会话规则

一次连接从建立到断开算一个**会话**。会话里的规矩就下面六条。

### 4.1 一问一答，不许并发

设备同时只处理一条命令。上一条的多帧响应还没发完就收到新请求 → 回
`ERR_BUSY`（4 字节帧，`TAG` 填**新请求**的 TAG，这样客户端知道是哪条被拒了）。

客户端必须等一条响应**收完**（最后一帧 `MORE = 0`）再发下一条。

### 4.2 先校验，后执行

收到帧的处理顺序是固定的：

```
查 CMD 是否已定义 ──不认识──> 回 ERR_UNKNOWN_CMD
        │
      认识
        ↓
查长度是否匹配 ────不匹配──> 回 ERR_BAD_LENGTH
        │
      匹配
        ↓
查模式要求 ───────不满足──> 回 ERR_WRONG_MODE
        │
      满足
        ↓
执行，回 OK + 数据
```

⚠ 前三步任一不过就立刻回错，**不产生任何副作用**——不动 flash、不改 RAM 工作
副本、不启停定时器。

### 4.3 断连即复位会话

连接断开时，设备要做完这五件事：

1. 清空发送队列；
2. 丢弃未发完的多帧响应；
3. 关闭传感器推流；
4. **退出标定模式**；
5. **丢弃标定模式下未提交的改动**（§6）。

⚠ 第 4、5 条是有意的：标定没做完就断线，本来就不该留下半套系数（理由见 07 §2.2）。

### 4.4 超时由客户端负责

**设备不为任何请求设超时**——它要么回一帧，要么就是没收到。所以超时判断全在
客户端：

| 命令类型 | 建议超时 | 理由 |
|---|---|---|
| 普通命令 | 1 秒 | 纯计算 + 一两帧通知 |
| `CFG_SAVE` | 3 秒 | 擦一页约 87ms + 写 |
| `REC_ERASE` | 3 秒 | 要擦 3 页，阻塞约 260ms |

⚠ 这一条只管"单条请求等不等得到应答"。设备另有一个**会话级**的计时器 —— 空闲断连
（§4.6），它判断的是"人还在不在"，与"这条请求超时"是两件事，不要混。

### 4.5 没有鉴权

任何连上的对端都能发任何命令。安全性靠两件事兜：

- **物理在场**：可连接窗口只能靠长按按键打开，且只开 30 秒；
- **确认码**：唯一会销毁数据的 `REC_ERASE` 需要 4 字节确认码防误触。

（这是有意接受的现状，取舍见 07 §2.5。）

### 4.6 空闲断连

**需求 7 的落地。** 连接建立后，若连续 `idle_disc_s` 秒没有收到**客户端请求**，
设备主动断开。

| 项 | 规则 |
|---|---|
| 计时起点 | 连接建立 |
| 重置条件 | **只认客户端请求**（收到一帧 ≥2 字节的下行数据）。设备自己发的推流帧（`TAG=0xFF`）**不重置** |
| 暂停条件 | 无（标定模式下同样生效） |
| 到期动作 | 先做 §4.3 的会话复位（清发送队列 → 丢未发完的响应 → 关推流 → 退标定模式 → 丢未提交改动），**再**断开 |
| 断开原因码 | `BLE_HCI_CONN_TERMINATED_BY_LOCAL_HOST` (0x16) |
| 默认值 | **300 秒**；`0` = 关闭 |
| 有效范围 | `0` 或 `30..65535` 秒 |

⚠ **客户端要按"随时可能掉线"来设计**：只盯着推流、长时间不发命令的连接会被断开。
需要长时间旁观实时重量时，周期性发一条 `CMD_SENSOR` 保活。

**客户端怎么识别"设备主动断开"**：原生栈能拿到 reason 0x16；Web Bluetooth 只给
`gattserverdisconnected` 事件、拿不到 reason，统一提示"连接已断开（可能空闲超时），
请长按设备按键重新连接"即可。

> 为什么要有这条、为什么只按请求重置、为什么没有标定看门狗，见 07 §2.3–2.4。

## 5. 命令详表

命令码分组：`0x0x` 只读信息 · `0x1x` 标定 · `0x2x` 配置 · `0x3x` 存储

| 码 | 名称 | 标定模式要求 | 一句话 |
|---|---|---|---|
| 0x01 | `INFO` | 任意 | 设备全部静态/摘要信息 |
| 0x02 | `SENSOR` | 任意 | 当前传感器快照 |
| 0x03 | `SENSOR_STREAM` | 任意 | 开/关传感器周期推流 |
| 0x10 | `CAL_GET` | 任意 | 读标定参数 |
| 0x11 | `CAL_ENTER` | 须**不在** | 进标定模式 |
| 0x12 | `CAL_EXIT` | 须**在** | 出标定模式 |
| 0x13 | `CAL_ZERO_SET` | 须**在** | 写零点（当前值或指定值） |
| 0x14 | `CAL_K_SET` | 须**在** | 写最小二乘系数 |
| 0x20 | `CFG_SET` | 任意 | 改饮料类型 / 广播参数 / 放置阈值 |
| 0x21 | `LINK_IDLE` | 任意 | 改空闲断连超时（0 = 关闭，§4.6） |
| 0x2F | `CFG_SAVE` | 任意 | 把 RAM 工作副本提交到 flash |
| 0x30 | `REC_READ` | 任意 | 分页下载记录 |
| 0x31 | `REC_ERASE` | 任意 | 清空全部记录（需确认码） |

### 0x01 `CMD_INFO` — 设备信息

**需求 1 的主要落地。** 参数：无（帧长 2）。

响应 DATA，共 **42 字节**（MTU 23 时 3 帧；MTU 247 时 1 帧）：

| 偏移 | 长 | 字段 | 来源 / 说明 |
|---|---|---|---|
| 0 | 1 | `cmd_proto_ver` | 本协议版本 = **1** |
| 1 | 1 | `fw_ver` | 固件版本，建议 `主<<4 \| 次` |
| 2 | 1 | `adv_proto_ver` | 广播包版本，即 `APP_PROTO_VERSION`（现 0x02） |
| 3 | 1 | `cfg_ver` | 配置结构版本，`APP_STORAGE_CFG_VERSION` |
| 4 | 6 | `mac[6]` | `sd_ble_gap_addr_get()` 的 `addr[]`，**小端原样** |
| 10 | 1 | `addr_type` | 1 = random static（默认，见 `ble_link.h`） |
| 11 | 4 | `device_id` | `FICR->DEVICEID[0]`，广播包里的 2 字节 ID 取其低 16 位 |
| 15 | 2 | `flags` | 见下表 |
| 17 | 1 | `drink_count` | 已启用饮料类型数，1..16 |
| 18 | 1 | `drink_idx` | 当前选中类型，`< drink_count` |
| 19 | 1 | `cal_epoch` | 标定世代号，每次 `CFG_SAVE` 改了标定就 +1（§7.3） |
| 20 | 2 | `rec_count` | 已写入记录条数 |
| 22 | 2 | `rec_capacity` | 容量，当前 **612** |
| 24 | 4 | `rec_seq_newest` | 最新记录的 `seq`；`rec_count==0` 时为 0xFFFFFFFF |
| 28 | 4 | `rec_seq_oldest` | 最旧记录的 `seq`；同上 |
| 32 | 2 | `batt_mv` | 当前电池电压 mV（现采一次 SAADC） |
| 34 | 2 | `adv_events` | 一轮广播事件数 |
| 36 | 2 | `adv_interval_ms` | 广播间隔 |
| 38 | 2 | `eff_mtu` | 设备侧有效 ATT MTU，**只读参考值**（建议客户端记日志；不得据此加长请求帧，§1.2） |
| 40 | 2 | `idle_disc_s` | 当前空闲断连秒数，`0` = 关闭（§4.6 / `CMD_LINK_IDLE`） |

`flags` 位定义：

| 位 | 名称 | 含义 |
|---|---|---|
| 0 | `CALIBRATED` | 已标定（`cal_k` 不全为 0） |
| 1 | `CAL_MODE` | 当前处于标定模式 |
| 2 | `STORAGE_READY` | `app_storage_init()` 成功（失败时记录功能不可用） |
| 3 | `CFG_DIRTY` | RAM 工作副本有未提交到 flash 的改动 |
| 4 | `STREAMING` | 传感器推流开着 |
| 5..15 | — | 保留，必须为 0 |

> `rec_seq_*` 供客户端做**增量下载**：记下上次拉到的 `seq`，下次只拉更新的部分。
> 标定系数刻意不放在 INFO 里（低频只读，拆到 `CAL_GET`），见 07 §3.6。

### 0x02 `CMD_SENSOR` — 当前传感器快照

**需求 2 的落地。** 参数：无（帧长 2）。

响应 DATA，共 **26 字节**（MTU 23 时 2 帧；MTU 247 时 1 帧）：

| 偏移 | 长 | 字段 | 说明 |
|---|---|---|---|
| 0 | 4 | `ch0` | int32，HX711 #1 chA，增益 128，**滑动平均后**的值 |
| 4 | 4 | `ch1` | int32，HX711 #1 chB，增益 32 |
| 8 | 4 | `ch2` | int32，HX711 #2 chA，增益 128 |
| 12 | 4 | `weight_g` | **float32 IEEE754**，`app_storage_weight_calc()` 的结果，单位克 |
| 16 | 2 | `batt_mv` | 电池电压 mV |
| 18 | 2 | `flags` | 数据状态，见下 |
| 20 | 4 | `sample_tick` | `m_sample_tick`，采样节拍序号 |


`flags` 位定义（低 8 位与 `app_proto.h` 的 `APP_PROTO_FLAG_*` **保持一致**，
高 8 位见 §7.3）：

| 位 | 名称 | 含义 |
|---|---|---|
| 0 | `STABLE` | 数据已稳定，可信 |
| 1 | `SETTLING` | 正在震荡 |
| 2 | `STALE` | 窗口过期，不可判定 |
| 3 | `UNCAL` | 未标定 → `weight_g` 恒为 0，不代表"真的 0 克" |
| 4 | `PRESENT` | **有物体放置**（新增，见下） |

⚠ `PRESENT` 判据：`|weight_g| >= cfg.present_thr_g`，**不要求 STABLE**。
未标定时该位无意义 —— 固件须置 `UNCAL` 并把 `PRESENT` 清 0。
（`STABLE/sample_tick` 为什么必须返回，见 07 §7 疏漏 5。）

---

### 0x03 `CMD_SENSOR_STREAM` — 传感器推流开关

参数（帧长 4）：

| 偏移 | 长 | 字段 | 说明 |
|---|---|---|---|
| 0 | 2 | `period_ms` | 推送周期，**0 = 关闭**；有效范围 100..10000 |

响应 DATA：2 字节 = 生效的 `period_ms`（设备可能上调到最小值 100）。

之后设备每 `period_ms` 主动推一帧 `CMD_SENSOR` 格式的响应（`TAG=0xFF`），
直到关闭、断连、或收到新的 `SENSOR_STREAM`。

建议周期 **200 ms**（传感器本身只有 7~10 Hz，更快没有信息量）。
推流帧与请求响应的发送优先级见 07 §4.4。

### 0x10 `CMD_CAL_GET` — 读标定参数

**需求 1 的"标定值/是否标定"。** 参数：无。任意模式可用。

响应 DATA，共 **26 字节**（MTU 23 时 2 帧；MTU 247 时 1 帧）：

| 偏移 | 长 | 字段 | 说明 |
|---|---|---|---|
| 0 | 12 | `cal_zero[3]` | int32 × 3，三通道零点 |
| 12 | 12 | `cal_k[3]` | **float32 × 3**，联合标定系数 |
| 24 | 1 | `cal_epoch` | 标定世代号 |
| 25 | 1 | `calibrated` | 0/1，等价于 `cal_k` 不全为 0 |

标定模型（与 `app_storage_weight_calc()` 及 `tool/solve_calibration.py` 一致）：

```
W = k0·(x0 − z0) + k1·(x1 − z1) + k2·(x2 − z2)
```

⚠ **三通道联合模型，不是逐通道增益。** `k_i` 是最小二乘权重，实测有一个是**负数**
（`k2 = −2.555e-03`）。不要对 `k` 的符号或量级做假设，也不要单独拿某个 `k_i` 换算
单通道重量。

⚠ 标定模式下返回的是 **RAM 工作副本**（可能含未提交改动）；否则返回 flash 里的值。
客户端靠 `INFO.flags.CFG_DIRTY` 区分。

---

### 0x11 `CMD_CAL_ENTER` — 进入标定模式

参数：无（帧长 2）。响应 DATA：无。

**没有看门狗，也没有超时参数。** 标定模式的退出只由三条路径决定（§6.2）：
`CAL_EXIT`、连接断开、收到 `REC_ERASE`。至于"客户端消失了怎么办" —— 由**空闲断连**
（§4.6）兜住：300 秒无请求就断开，而断连本身就会退出标定模式。

已在标定模式时重复调用 → `ERR_WRONG_MODE`。

进入后设备行为变化见 §6。

---

### 0x12 `CMD_CAL_EXIT` — 退出标定模式

参数（帧长 3）：

| 偏移 | 长 | 字段 | 说明 |
|---|---|---|---|
| 0 | 1 | `save` | 0 = **丢弃**未提交的改动；1 = 提交到 flash（等价于先 `CFG_SAVE`） |

响应 DATA：1 字节 = 实际是否写了 flash（0/1）。

`save=1` 而标定参数非法（规则同 `CAL_K_SET`：NaN / Inf）→ `ERR_BAD_PARAM`，
**且不退出模式**，让客户端有机会改正。

设备也会在这两种情况下**自行退出**（等价于 `save=0`）：

1. 连接断开（包括空闲断连，§4.6）；
2. 收到 `REC_ERASE` → 同时主动推一帧 `0x12|0x80, TAG=0xFF` 告知。

---

### 0x13 `CMD_CAL_ZERO_SET` — 写零点

**须在标定模式**，否则 `ERR_WRONG_MODE`。参数（帧长 3 或 15）：

| 偏移 | 长 | 字段 | 说明 |
|---|---|---|---|
| 0 | 1 | `mode` | 0 = **取设备当前三通道滑动平均**作为零点（帧长 3）<br>1 = 用下面给定的值（帧长 15） |
| 1 | 12 | `zero[3]` | int32 × 3，仅 `mode=1` 时存在 |

响应 DATA：12 字节 = 实际生效的 `zero[3]`（`mode=0` 时客户端据此知道取到了什么）。

`mode=0` 且当前数据不是 `STABLE` → **仍然执行，但响应 `STATUS=OK`**，
客户端应自行先确认 `SENSOR.flags.STABLE` 再调用。

**只改 RAM 工作副本，不落盘**（见 §7.1）。

---

### 0x14 `CMD_CAL_K_SET` — 写最小二乘系数

**须在标定模式**。参数（帧长 14）：

| 偏移 | 长 | 字段 | 说明 |
|---|---|---|---|
| 0 | 12 | `k[3]` | **float32 × 3**，IEEE754 小端 |

响应 DATA：无（帧长 4）。

固件校验：任一 `k_i` 为 NaN / Inf → `ERR_BAD_PARAM`。
**允许负数与 0**（负数是实测事实，全 0 表示"标为未标定"）。

**只改 RAM 工作副本，不落盘。** 改完立即生效 —— 客户端可马上用
`CMD_SENSOR` 看新系数算出来的重量对不对，不满意就再下发一组，
全程不碰 flash。

---

### 0x20 `CMD_CFG_SET` — 改配置

任意模式可用。参数（帧长 4 ~ 12：`2` 帧头 + `2` 掩码 + 最多 `8` 字节值）：

| 偏移 | 长 | 字段 | 说明 |
|---|---|---|---|
| 0 | 2 | `mask` | 位掩码，选择本次要改哪些字段 |
| 2 | … | 值 | 按 `mask` 中置位的字段，**按位号从低到高依次紧密排列** |

| 位 | 字段 | 类型 | 范围 |
|---|---|---|---|
| 0 | `drink_idx` | u8 | `< drink_count` |
| 1 | `drink_count` | u8 | 1..16 |
| 2 | `adv_events` | u16 | ≥ 1 |
| 3 | `adv_interval_ms` | u16 | 20..10240 |
| 4 | `present_thr_g` | i16 | 1..2000，单位克（新增字段） |

响应 DATA：无。

同时改 `drink_count` 与 `drink_idx` 时，固件按**改完之后的值**统一校验
（`drink_idx < drink_count`），避免"先设 idx 再设 count"的中间态被拒。

**只改 RAM 工作副本，不落盘。**

⚠ 帧长随 `mask` 变化：固件必须先按 `mask` 算出期望长度再校验，不符回 `ERR_BAD_LENGTH`。

---

### 0x21 `CMD_LINK_IDLE` — 空闲断连超时

**需求 7 的落地。** 任意模式可用。参数（帧长 4）：

| 偏移 | 长 | 字段 | 说明 |
|---|---|---|---|
| 0 | 2 | `idle_s` | 空闲断连秒数；**0 = 关闭**；有效 `0` 或 `30..65535` |

响应 DATA：2 字节 = 生效的 `idle_s`（客户端据此知道设备是否接受了它给的值）。

- `1..29` → `ERR_BAD_PARAM`（低于 30 秒没有意义，还会打断正常的批量下载）；
- 计时器在本应答**发出之后**重新起算 —— 改完不会立刻被自己刚设的短超时踢掉；
- **只改 RAM 工作副本，不落盘**，需 `CFG_SAVE` 才持久化（与 §7.1 一致）。

行为细节（计时起点、重置条件）见 **§4.6**。

---

### 0x2F `CMD_CFG_SAVE` — 提交到 flash

任意模式可用。参数：无。

响应 DATA：1 字节 = 新的 `cal_epoch`。

行为：把 RAM 工作副本整体写入配置页（`app_storage_cfg_save()`：先校验 → 擦一页 → 写）。
若本次提交改动了 `cal_zero` 或 `cal_k`，则 `cal_epoch` 先 +1 再写。

校验不过 → `ERR_BAD_PARAM`，**不擦不写**（`app_storage_cfg_save()` 已经是这个顺序）。
fstorage 失败 → `ERR_STORAGE`。

**阻塞约 90~180ms**（擦一页 87ms + 写）。客户端超时给 3s。

⚠ 本命令与 `CAL_*_SET` / `CFG_SET` 一样**只改 RAM**，断电或断连会丢未提交的改动；
要持久化必须显式调用 `CFG_SAVE`（理由见 07 §3.1）。

---

### 0x30 `CMD_REC_READ` — 分页下载记录

**需求 5 的落地。** 任意模式可用。参数（帧长 5）：

| 偏移 | 长 | 字段 | 说明 |
|---|---|---|---|
| 0 | 2 | `idx` | 起始索引，**0 = 最新一条**（与 `app_storage_rec_get()` 同向） |
| 2 | 1 | `count` | 请求条数，1..**64** |

响应 DATA：`1 + n × 20` 字节

| 偏移 | 长 | 字段 |
|---|---|---|
| 0 | 1 | `n` — 实际返回条数，可能 < `count`（读到末尾） |
| 1 | 20×n | 记录流，每条 20 字节，格式见 §7.4 |

- `idx >= rec_count` → `ERR_NOT_FOUND`；
- `count = 0` 或 `> 64` → `ERR_BAD_PARAM`；
- `n = 0` 不会出现（`idx` 合法就至少有 1 条）；
- `count=64` 时 DATA = 1281 字节：MTU 247 下 6 帧，MTU 23 下 81 帧（都在 128 帧内）。

**全量下载流程**：读 `INFO.rec_count` → 从 `idx=0` 起以 32 或 64 为步长循环，
直到累计条数达到 `rec_count`。

⚠ **下载期间不保证快照一致性**：若此刻有人按键存了新记录，索引会整体后移一位，
客户端可能重复拿到一条或漏掉一条。**客户端必须按 `seq` 去重**（`seq` 全局单调递增），
重复的丢掉、缺的下一轮补。这也顺带支持断点续传与增量下载。

⚠ **只返回原始计数，不返回算好的重量** —— 重量依赖会变的标定参数，客户端应能重算。
记录里的 `cal_epoch`（§7.3）标明每条是哪套系数采的。

（这两条取舍的论证见 07 §3.3 / §3.4。）

---

### 0x31 `CMD_REC_ERASE` — 清空全部记录

**需求 5 的落地。** 任意模式可用（但会强制退出标定模式，见下）。参数（帧长 6）：

| 偏移 | 长 | 字段 | 说明 |
|---|---|---|---|
| 0 | 4 | `confirm` | 必须等于 **0x53415245**（ASCII `'ERAS'` 小端） |

响应 DATA：无。`confirm` 不符 → `ERR_CONFIRM`，**不擦任何东西**。

行为：`app_storage_rec_erase_all()`，擦 3 页，**阻塞约 260ms**，
然后 `rec_count`/`seq` 全部归零。客户端超时给 3s。

- 处于标定模式时收到本命令 → **先自动退出标定模式（丢弃未提交改动），再执行擦除**。
  理由：标定模式的语义是"停止记录数据"，而擦除是记录区的重大操作，
  两者叠加的状态没人能说清；强制收敛到一个明确状态。
  响应仍是 `REC_ERASE` 的，同时另发一帧 `0x12|0x80, TAG=0xFF` 告知模式变化。

⚠ 擦除后 `seq` 归零，客户端**必须能容忍 `seq` 回退** —— 把它当成"换了一批数据"，
清空本地缓存。（为什么需要确认码，见 07 §3.5。）

## 6. 设备模式与标定模式的副作用

### 6.1 两个模式

| | 普通模式 | 标定模式 |
|---|---|---|
| 单击按键 | LED 闪 + 播数据广播 + 存一条记录 | **LED 闪一下，其余全部抑制**（不播、不存） |
| 长按按键 | 开可连接窗口 | 同（已连接时无意义） |
| 双击按键 | 关窗口 / 断开 | 同（保留退路，见下） |
| 数据广播 | 单击触发 | **完全抑制** |
| 记录写入 | 单击时写一条 | **完全抑制** |
| HX711 采样 | 正常 100ms 节拍 | **正常，不受影响** |
| 标定参数 | 用 flash 里的值 | 用 RAM 工作副本（可含未提交改动） |

**需求 4 的落地。** 三点要说清：

1. **"停止广播"指的是数据广播（`ble_beacon`）**，不含可连接广播 —— 后者必须留着，
   否则断连后就再也连不上，只能靠物理长按。所以标定模式真正要拦的是
   "单击 → `adv_policy_burst_data()`"这条路径。
2. **单击仍然闪一下 LED。** 完全没反应会让人以为设备挂了；闪灯表示
   "收到了，但当前模式不干这个"。
3. **双击/长按行为不变。** 标定模式下必须保留一条不依赖蓝牙的退路 ——
   万一上位机崩了，用户还能双击断开连接（触发断连 → 自动退出标定模式）。

### 6.2 标定模式怎么退出

退出路径只有三条（除 `save=1` 会提交外，其余都等价于丢弃未提交的改动）：

| 路径 | 说明 |
|---|---|
| `CMD_CAL_EXIT` | 客户端主动退出；`save=1` 时先提交到 flash |
| **连接断开** | 含空闲断连（§4.6）：300 秒无请求 → 断开 → 自动退出 |
| `CMD_REC_ERASE` | 强制先退出，再擦除；同时推一帧 `0x12\|0x80, TAG=0xFF` 告知 |

**没有看门狗、没有超时参数** —— "客户端消失了"由空闲断连兜住（§4.6），不需要第二套
计时器。客户端因此要保证：标定期间只要人还在，就有命令在发（推流期间的轮询即可）。

⚠ 固件应在标定模式下让 LED **慢闪**（`DRV_LED_BLINK_SLOW`），给一个外部可见的状态
指示 —— 快闪已被"可连接窗口"占用，常亮被"已连接"占用，慢闪空着正好。

> 为什么最终删掉标定看门狗、以及 `idle_disc_s = 0` 时的风险，见 07 §2.4。

## 7. 数据结构与固件对应关系

### 7.1 配置的 RAM 工作副本

固件只有一份 `static app_storage_cfg_t m_cfg`（`main.c`），开机由
`app_storage_cfg_load()` 填充。本协议把它当作**工作副本**：

```
flash 配置页  ──load──▶  m_cfg (RAM)  ──▶ weight_calc / 广播 / 记录
                            ▲                    
                            │ CAL_*_SET / CFG_SET 直接改这里(立即生效)
                            │
                         CFG_SAVE ──save──▶ flash 配置页
```

需要新增一个 `m_cfg_dirty` 标志（对应 `INFO.flags.CFG_DIRTY`）。
为什么要这样设计，见 07 §3.1。

### 7.2 `app_storage_cfg_t` 需要扩展（cfg v2 → v3）

现状 36 字节。本协议需要三个新字段：

| 新字段 | 类型 | 用途 |
|---|---|---|
| `present_thr_g` | `int16_t` | `PRESENT` 位的判定阈值，默认 **5** 克 |
| `idle_disc_s` | `uint16_t` | 空闲断连秒数，默认 **300**，`0` = 关闭（§4.6） |
| `cal_epoch` | `uint8_t` | 标定世代号，`CFG_SAVE` 改了标定就 +1 |
| （填充） | `uint8_t[3]` | 保持 4 字节对齐（`36+2+2+1 = 41`，补 3 字节到 44） |

→ **44 字节**，仍满足 `% 4 == 0`。两个 u16 落在偶偏移（36 / 38）上，无需 packing。

⚠ 按 `app_storage.h` 自己写明的规则：**加字段只能往尾部加，并递增
`APP_STORAGE_CFG_VERSION`（2 → 3）**。老设备升级后 version 不匹配 →
`cfg_load()` 回退默认值，**标定参数会丢，需要重新标定**。这是有意的保守行为，
但**升级前要提醒用户先用 `CAL_GET` 把系数抄下来**。

`present_thr_g` 默认 5 克的理由：噪声底噪 ±30 counts ≈ 0.08 g，
最不灵敏的 ch1 是 49.3 counts/g；5 克远高于噪声，又远低于任何真实杯子的重量。

### 7.3 `flags` 字段的统一布局（16 位）

`CMD_SENSOR` 的 `flags`、`app_storage_rec_t.flags`、以及广播协议里的数据状态位
**共用低 8 位定义**，避免三处各写一套：

| 位 | 名称 | 定义于 |
|---|---|---|
| 0 | `STABLE` | `app_proto.h`（已有） |
| 1 | `SETTLING` | `app_proto.h`（已有） |
| 2 | `STALE` | `app_proto.h`（已有） |
| 3 | `UNCAL` | `app_proto.h`（已有） |
| 4 | `PRESENT` | **本协议新增** |
| 5..7 | 保留 | 必须为 0 |
| 8..15 | `cal_epoch` | **本协议新增**：写记录时的标定世代号 |

（为什么塞在 `flags` 里而不新增字段，见 07 §3.2。）

### 7.4 记录的线路格式（20 字节，与 `app_storage_rec_t` 逐字节一致）

| 偏移 | 长 | 字段 | 说明 |
|---|---|---|---|
| 0 | 4 | `seq` | u32，全局单调递增；`0xFFFFFFFF` 不会出现（那是空槽标志） |
| 4 | 2 | `batt_mv` | u16，电池电压 mV |
| 6 | 2 | `flags` | 见 §7.3 |
| 8 | 12 | `ch[3]` | int32 × 3，三通道原始计数（已符号扩展的 24bit） |

固件可以直接 `memcpy` 结构体上线路，无需逐字段打包 —— 线路格式刻意等于内存布局。

⚠ `batt_mv` 单位必须是 **mV**。固件当前存的是 ADC 原始计数（漏了换算），实现本协议
前必修，否则新旧记录语义不一致（详见 07 §4.5）。

## 8. 标定作业流程（客户端实现参考）

这是协议的主要使用场景，也是核对协议是否够用的最佳检验。

```
 1. 长按按键 → 30s 可连接窗口 → 连接 → 使能 TX 通知
 2. CMD_INFO                      拿版本号、是否已标定、cal_epoch
 3. CMD_CAL_GET                   抄下现有系数（万一要回滚 / 或升级前备份）
 4. CMD_CAL_ENTER                进标定模式（设备停播、停记录、LED 慢闪）
                                   无参数；退出靠 CAL_EXIT / 断连 / REC_ERASE（§6.2）
 5. CMD_SENSOR_STREAM(200)        开推流，界面上实时显示三通道与重量
 6. 清空秤台
    等 flags.STABLE
    CMD_CAL_ZERO_SET(mode=0)      取当前滑动平均作为零点 z[]
 7. 对每个已知砝码 m_j (至少 3 个，建议 4~6 个覆盖量程):
       放上砝码
       等 flags.STABLE
       记下 (x0,x1,x2) 与 m_j
 8. 上位机解线性方程组求 k[]:
       [x0-z0  x1-z1  x2-z2]_j · k = m_j
       3 组样本 → 恰定，直接解（见 dev/tool/solve_calibration.py）
       >3 组    → 超定，最小二乘
 9. CMD_CAL_K_SET(k[])            下发，立即生效（仍在 RAM）
10. 复核: 放一个未参与拟合的砝码 → CMD_SENSOR → 看 weight_g 误差
       不满意 → 回第 7 步补样本，重解，重下发（不碰 flash）
11. CMD_CFG_SET(mask=present_thr_g, ...)   顺便设放置阈值
12. CMD_CAL_EXIT(save=1)          提交到 flash，cal_epoch +1，退出标定模式
13. CMD_SENSOR_STREAM(0)          关推流
14. 双击按键 或 断开连接
```

⚠ **第 7 步为什么至少 3 个砝码**：模型有 3 个未知数 `k0/k1/k2`。
`tool/solve_calibration.py` 里那组真实数据就是 3 个砝码（200/300/400 g）恰定求解。
只放 1~2 个砝码方程欠定，解出来的 `k` 是任意的。

⚠ **砝码要覆盖量程且互不成比例**。三个砝码若读数近似成比例，
矩阵接近奇异，解出的 `k` 会被噪声放大到毫无意义。上位机应检查条件数并给警告。

## 9. 版本号一览（四个，别搞混）

| 版本号 | 值 | 定义处 | 变更条件 |
|---|---|---|---|
| `CMD_PROTO_VERSION` | **1** | 本文 / `cmd_proto.h`（待建） | 本协议的帧格式或命令语义变化 |
| `APP_PROTO_VERSION` | 0x02（v3 已设计未接线） | `main.c` / `app_proto.h` | 广播包布局变化 |
| `APP_STORAGE_CFG_VERSION` | 2 → **3**（本协议要求） | `app_storage.h` | 配置结构布局变化 |
| `fw_ver` | 待定 | 建议新增 | 每次发布固件 |

客户端策略：先 `CMD_INFO`，比对 `cmd_proto_ver`。不认识的版本**拒绝操作**
而不是猜着用 —— 尤其不能猜着发 `CAL_K_SET` 或 `REC_ERASE`。

⚠ "下行钉死 20 / 上行按协商 MTU"（§1.2）虽然是**语义变化**，但固件与客户端都还
没按 v1 上线，所以不算破坏兼容，**仍留在 v1**，不升版本号。

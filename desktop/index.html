使用说明 / 排查
串口模式
  1. 需 Chrome / Edge 89+(Web Serial API)。Firefox / Safari 不支持。
  2. 本页可直接以 file:// 打开;若浏览器拒绝,用 python -m http.server 后访问 localhost。
  3. 设备日志走 UART: TX = P0.06, 115200 8N1 (来自 sdk_config.h)。DK 板经板载 CH340/J-Link CDC 虚拟串口输出。
  4. 串口是独占的 —— 先关掉 RTT Viewer / 串口助手 / nRF Connect,否则连不上。
BLE 模式
  1. 本页必须经 https 或 localhost 打开。file:// 不是安全上下文, Web Bluetooth 直接不可用。用 python -m http.server 然后访问 http://localhost:8000/index.html。
  2. 扫描还需在 chrome://flags/#enable-experimental-web-platform-features 开启实验特性并重启浏览器 —— requestLEScan() 至今仍是实验 API。 「连接设备」不需要这个开关。
  3. ⚠ 设备平时是静默的: 固件平时不播任何广播。 单击按键才播 3 个广播事件(同一份数据), 所以"扫描已启动但报文区一直空着"是正常的,需要有人去按键。
  4. ⚠ 连接前要先长按按键: 可连接广播只在长按后开 30 秒窗口(BLE_LINK_ADV_DURATION_MS)。 窗口外点「连接设备」,弹窗里会是空的。
  5. ⚠ 扫描与连接互斥: 协议栈只有一个广播集, 可连接窗口期间数据广播是停掉的,此时扫描收不到数据包属于预期。
  6. 部分系统(尤其 Linux / 某些 Windows 配置)扫描需要定位权限或 蓝牙适配器处于可扫描状态;报错时先确认系统蓝牙已开。
通用
  1. 点"模拟数据"可在无硬件时验证解析与绘图,两种模式各有对应的模拟器 (BLE 模拟器会重现"一次按键 9 个相同包"的去重场景)。
  2. 标定工具: 需至少 3 个不同重量点的样本, 且三个通道都要有 变化(否则矩阵奇异, 无法解出 k)。数据源选 avg 时须等滑动平均 窗口产生数值(白色虚线变为实线之后)再采样。
波形为何呈阶梯状? 固件每 100ms 打印一行,但 HX711 并非每次都有新值。 曲线按"采样保持"绘制(保持上一已知值),实心点标记真正的新帧。 #1 在 A/B 批次切换处需约 400ms 重新稳定,会出现明显平台段,属正常现象。
BLE 模式下的图为什么这么稀疏? 因为一次按键才有一个数据点 —— 广播载荷里放的是三通道滑动平均值(固件 payload_refresh() 取 ma_avg()),不是原始流。想看连续波形请用串口模式。 同理,BLE 模式下右侧"数据源 raw/avg"选择器被隐藏 —— 载荷格式由固件钉死,没有可选项。
报文区的颜色对应负载布局的字段边界: 魔数+版本、 设备ID、 计数器、 电池、 ch0、 ch1、 ch2。 标"(重播)"的行是同一计数器的重复包 —— 只记录不入图。
三通道增益不同: ch0/ch2 = 128,ch1(chB) 硬件固定 = 32。 原始计数不可直接横向比较,勾选"按增益归一化"可折算到同一尺度。
白色阶梯线 = 网页端算的滑动平均。 规则与固件 ma_push() 一致 —— 只有新帧入窗, 未就绪 tick 重复打印的保持值不计入(否则停留越久的值权重越大, 结果会和设备端不符)。窗口未满时画虚线,对应固件 ma_ready() 为假、平均尚不可信的阶段,头部同时显示 (n/窗口) 进度。
⚠ 数据源选 avg 时,设备端已做过一次平均,此处再平均 等于二次滤波,响应会更迟钝。想比对网页与固件的算法是否一致, 应选 raw 看白线,再切到 avg 看固件输出, 两者应当接近(固件为整数除法,有 ±1 量级的舍入差)。 BLE 模式下载荷本身就是平均值,等同于选了 avg。
